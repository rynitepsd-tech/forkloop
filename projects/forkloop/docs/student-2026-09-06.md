## Step 2 — the milestone staircase (built before the probes, commit bf8196a)

`ClaimsOpsWorld.ui_milestones` runs after the oracle and stores, under `verdict.details["ui_milestones"]` and with no
effect on the reward, the rungs `openemr_login` (a `log` row `event LIKE 'login%'` with `success` 1 after the
watermark; failures counted alongside), `openemr_chart` (a `log` row keyed by the target patient, or an audited request
path under `patient_file`), `openemr_document` (an `http-request` row whose base64-decoded path is a document view),
`portal_claim` and `portal_appeal_form` (`page_views` paths of the target claim), `appeal_submitted` (an `appeals`
row). `scripts/milestone_staircase.py` prints the percentages per run and adds two trajectory rungs, `login_page`
(the task's username typed) and `auth_typed` (the expected authorization number typed anywhere). Three offline tests
on the fake backend (seeded audit rows on a verified and on a failed episode; the script on a recorded run with and
without the rungs). The live evidence matched the detector on the first probe: OpenEMR 8.3 logs `login` rows with
`success` 0/1 and `http-request-update` rows whose base64 comments are the request path.

**The three 2026-09-05 runs cannot be re-read with it**: their verdicts predate the rungs and the machines are gone,
so the database rungs print "needs a re-run"; only the trajectory rungs apply to them (`login_page` 30/30 in the two
`--nav-macro` runs, `auth_typed` 0/30 everywhere), which is the same picture the ledger already drew by hand.

**The histogram, past the login.** Every episode logs into OpenEMR (73 successful logins over the run, 2.4 per
episode; 151 failed ones, mostly `admin` retyped into the Password field once the fields were cleared) and every one
dies between the login and the patient chart. Per-episode table in `runs/logs/postlogin-fara15-4b-fair.md`:

- **Navigation by invented URL, 25/30 episodes (92 `visit_url` calls with made-up OpenEMR paths, 242 macro
  expansions in all).** Inside OpenEMR the model clicks the *Patient* menu once or twice, then reaches for
  `visit_url` — `/openemr/login.php`, `/openemr/index.php?route=login`, `/openemr/interface/main.php?…&pat_id=C-60206`,
  `/openemr/interface/login/login.php?username=admin&password=pass` — which lands on a 404, a blank page or the login
  page, and it logs in again. The loop is login → calendar → guessed URL → login; 17/30 also flip to the portal
  (`localhost:8080`) and back. This is the browser-harness habit the nav macro made executable: a base Fara that
  cannot navigate by clicking through OpenEMR's menus navigates by URL, and OpenEMR has no guessable URLs.
- **Chrome's post-login crash, 12/30 episodes** ("Aw, Snap! Error code: 5" on `interface/main/tabs/main.php`, then
  Reload → login page again). The prompt's reload rule is followed; the session is gone after the crash.
- **Zero `ask_user_question` stops** (the no-user prompt removed the whole class), zero wrong-record, collateral,
